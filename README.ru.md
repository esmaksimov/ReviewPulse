# ReviewPulse

[English](README.md) · [Русский](README.ru.md) · [Español](README.es.md) · [Italiano](README.it.md) · [中文](README.zh.md)

Телеграм-бот, который следит, чтобы ревью не зависало: ведёт статус по каждому
назначенному ревьюверу и пишет в личку тому, на ком сейчас мяч — строго в рабочее время.

Ловит два случая:

1. Ревьювер вообще не отреагировал, а MR висит.
2. Ревьювер поставил «нужны правки», автор всё поправил и закрыл треды, но ревьювер
   не вернулся и апрув не поставил. Формально мяч на нём, но его никто не дёргает.

При этом если после правок ревьювер **снова** попросил поправить — мяч возвращается
автору и напоминания прекращаются: бот никогда не дёргает того, кто уже сделал своё.

## Быстрый старт

Готовый образ: [`s1k0de/reviewpulse`](https://hub.docker.com/r/s1k0de/reviewpulse)
(linux/amd64 + linux/arm64). Ничего собирать не нужно.

**1. Заведите бота** у [@BotFather](https://t.me/BotFather), скопируйте токен. Там же:
`/setprivacy` → **Disable** — иначе бот не увидит пост, автоматически скопированный в
группу обсуждений.

**2. Добавьте бота** администратором в канал ревью — с правами **Публикация
сообщений** (для `/announce`) и **Удаление сообщений** (чтобы пост закрытого ревью
сам пропадал из канала) — **и** участником в привязанную к нему группу обсуждений
(комментарии должны быть включены).

**3. Запустите** — выберите вариант под свой способ деплоя:

Compose стоит оставить у себя насовсем — именно его вы будете править, когда захотите
поменять настройку, а `--profile postgres` включается одним флагом, если он вообще
понадобится (см. [Какую БД брать](#какую-бд-брать) ниже).

Всё остальное имеет разумные значения по умолчанию: SLA 2 часа, повтор раз в 20 минут,
не больше 8 напоминаний в день, ревью закрывается, когда апрувнул каждый названный
ревьювер. Полный список — в [`.env.example`](.env.example).

**4. Каждый ревьювер один раз пишет боту `/start`.** Telegram запрещает боту писать
первым — без этого напоминания физически не дойдут. Если назначенный ревьювер не
зарегистрирован, бот один раз скажет об этом в ветке комментариев.

### Какую БД брать

**Берите SQLite** — он по умолчанию и его достаточно. Бот однопоточный, пишет
десятки строк в день; вся база — один файл на volume, бэкап это `cp`.

Postgres имеет смысл, только если он у вас и так есть или нужны штатные бэкапы:

```bash
docker compose --profile postgres up -d
```
и в `.env`:
```dotenv
DATABASE_URL=postgresql+asyncpg://reviewpulse:reviewpulse@db:5432/reviewpulse
```

Схема и миграции одинаковые, обе БД проверены end to end. Миграции применяются сами
при старте.

## Как это выглядит

Бот разбирает посты по форме, а не по жёсткому шаблону — годятся оба варианта ниже.
Чтобы пост вообще считался ревью, нужно одно из двух: **хотя бы одна ссылка на MR**
или **явно размеченная строка с ревьюверами** (тогда доработка без кода — например,
только по конфигу или инфре — тоже отследится, если ревьюверы названы явно). Без
этого пост считается объявлением и не отслеживается.

> Метки («Ревью:», «MR:», «Документация:», ...) распознаются на всех языках, которые
> понимает сам бот — команда, пишущая посты на испанском или китайском, получит тот же
> разбор, что и русско- или англоязычная. См. [Поддержка языков](#поддержка-языков).

Пост в канале:

```
Платежи

Доработка connection pool

MR API: https://gitlab.example.com/backend/services/api_controller/-/merge_requests/1112

MR Utils: https://gitlab.example.com/backend/packages/utils/-/merge_requests/223

Задача: https://tasks.example.com/space/2829/boards/card/3517380

Ревью: @user1 @user2
```

Более строгий шаблон — тоже понимается:

```
Каталог
Оплата картой: Починить редирект

MR: https://gitlab.example.com/backend/services/checkout/-/merge_requests/77

Документация: https://wiki.example.com/pages/12345
Описание: Если документация отсутствует
Ревьювер: @user2 для бэка / @user1 для остальных, @user3
```

Что бот берёт из поста:

| Что | Откуда |
|---|---|
| продукт | первая непустая строка |
| задача | следующая строка, не являющаяся полем или ссылкой |
| MR | **все** ссылки вида `…/-/merge_requests/<N>`, сколько бы их ни было |
| ревьюверы | все `@ник` в строке на «Ревью…»; иначе — все `@ник` в посте |

Ссылки на трекер и вики за MR не принимаются. Проза на строке ревьюверов не мешает
вытащить ники. Если ревьюверов распознать не удалось, бот не молчит: карточка выйдет с
кнопкой «🙋 Я ревьювер».

### Автогенерация поста

Вместо того чтобы вручную набирать весь шаблон, пусть его соберёт бот: он сам
подставит название продукта, подберёт ревьюверов и опубликует пост в канал.

Нажмите **📢 Анонс** в меню бота (или отправьте просто `/announce`) — он спросит по
одному пункту за сообщение: название, ссылки на MR/PR, документацию, задачу; у каждого
необязательного шага есть кнопка **⏭ Пропустить**. То, что каждый ответ приходит
отдельным сообщением, попутно чинит и вставленные гиперссылки: строка
`Документация: Confluence`, где *Confluence* — ссылка, не содержит URL в тексте вообще,
и чтение только текста раньше приводило к посту с молча пропавшей документацией.

Дальше есть две развилки:

- **Совсем нет MR/PR** — правка только в SQL или изменение документации — и бот
  спросит, к какому продукту это относится: вывести его неоткуда, репозитория нет.
  Пост всё равно будет отслеживаться: явной строки с ревьюверами достаточно,
  merge request не обязателен.
- **Нет ссылки на документацию** — бот предложит вместо неё текстовое **Описание**,
  которое уйдёт в пост строкой `Описание:`, как в шаблоне.

Если текст уже готов и лежит в буфере, старая форма одним сообщением тоже работает:

```
/announce Доработка connection pool
https://gitlab.example.com/example/demo-project/-/merge_requests/1112
Документация: https://wiki.example.com/pages/1
```

В обоих случаях бот пришлёт превью с тремя кнопками — **Опубликовать**,
**🔁 Другой ревьювер**, **Отмена**: можно перевыбрать, если выпавший ревьювер, скажем,
в отпуске, или отменить черновик целиком. После публикации пост проходит тот же путь
разбора и трекинга, что и написанный вручную — никакой особой логики для него нет.

Подбор ревьюверов настраивается через окружение, одна запись на GitLab-проект, ключ —
тот же `project_path`, что уже есть в ссылке на MR:

```dotenv
REVIEW_PROJECTS={"example/demo-project":{"product":"Demo Product","techlead":"user1","reviewer_count":2}}
```

- `product` — показывается в сгенерированном посте.
- `techlead` *(опционально)* — включается всегда, кроме случая, когда `/announce`
  запускает он сам. Переопределяется по продукту через `/manage`, без правки `.env` —
  см. [Управление через бота](#управление-через-бота).
- `reviewer_count` *(опционально, по умолчанию 2)* — сколько всего ревьюверов на
  посте, включая техлида.

Ключ, оканчивающийся на `/*`, например `"example/*"` — это префикс по умолчанию: он
покрывает любой репозиторий из этой группы/подгруппы GitLab, для которого нет
отдельной записи, так что новый репозиторий сразу работает с `/announce`, без
необходимости сначала добавлять его вручную. Точная запись всегда важнее wildcard, а
более специфичный (длинный) wildcard — важнее более общего.

Оставшийся слот(ы) заполняются из **пула ревьюверов этого продукта** — см.
[Управление через бота](#управление-через-бота) ниже. Нажми **📦 Продукты** в меню
бота (или отправь `/products`), чтобы увидеть настройку `REVIEW_PROJECTS` прямо в
Telegram, не открывая `.env` — по каждому продукту, его обязательному ревьюверу и
тому, кто сейчас в его пуле.

Строка «Автор:» заполняется бесплатно — в отличие от ручного поста, личность автора
уже известна из личной переписки с ботом, никакой отдельной метки не нужно.

Можно назвать несколько ссылок на MR сразу — например, сам сервис и его helm-чарт —
это нормально, если у всех одинаковый набор ревьюверов (техлид и reviewer_count в
`REVIEW_PROJECTS`; разный `product` сам по себе конфликтом не считается — берётся
продукт первого названного проекта). Если проекты реально расходятся в том, кто
ревьюит — черновик отклоняется с именами конфликтующих проектов, а не молча берёт
один из них.

### Вложения файлов

Последний шаг составления поста перед превью — **📎 Файлы**: пришлите одну или
несколько фотографий или документов, затем нажмите **✅ Готово** (или пропустите шаг
совсем без файлов). Telegram и так хранит всё, что присылают боту, поэтому ничего
дополнительно не настраивается: бот просто запоминает `file_id` каждого файла в
черновике и пересылает их отдельными сообщениями сразу после публикации поста — один
файл как есть, несколько — одним альбомом (`send_media_group`, не больше 10 за раз —
ограничение самого Telegram).

Карточка, которая появляется в ветке комментариев под постом:

```
🤖 Платежи — Доработка connection pool

   Апрувы: 1/2

   • @user1 — 👍 апрув
   • @user2 — 🔁 правки готовы, ждёт повторного взгляда

   api_controller!1112
   utils!223

   [👍 Апрув]     [✍️ Поправить]
   [✅ Поправил]  [🗄 Закрыть]
```

А тому, на ком завис мяч, приходит в личку:

```
🔁 Замечания закрыты, а ✍️ висит

Автор поправил всё, что ты просил, но апрува от тебя пока нет.

Платежи — Доработка connection pool
Просрочка: 1 ч 20 мин рабочего времени

https://gitlab.example.com/backend/services/api_controller/-/merge_requests/1112

Открыть обсуждение

   [🔕 Час]  [🔕 До завтра]
```

## Почему кнопки, а не реакции

**В каналах Telegram реакции анонимны.** Бот-администратор получает только
`message_reaction_count` (агрегат «👍 2»), но не `message_reaction` с полем `user`.
Персональные реакции приходят исключительно в группах и супергруппах — узнать,
*кто именно* поставил 👍 на пост канала, нельзя ни ботом, ни userbot'ом через MTProto,
Telegram эту информацию не отдаёт вообще.
См. [Bot API](https://core.telegram.org/bots/api#update) и
[api/reactions](https://core.telegram.org/api/reactions).

Поэтому бот публикует **свою карточку с инлайн-кнопками** в ветке комментариев под
постом. `callback_query` всегда содержит `from.id`, так что состояние по каждому
ревьюверу достоверно на 100%. Сам канал и формат постов при этом не меняются.

Механика:

```
пост в канале
     │
     │  Telegram сам копирует его в привязанную группу обсуждений
     ▼
копия в группе  ──►  бот отвечает на неё карточкой  ──►  карточка попадает
                     с инлайн-кнопками                   в ветку комментариев
                            │
                            │  нажатие кнопки = callback_query,
                            ▼  в нём всегда есть from.id
                     достоверный статус по каждому ревьюверу
```

Оба апдейта — пост в канале и его копия в группе — приходят в непредсказуемом
порядке, поэтому обе ветки делают upsert по одному ключу, а карточку публикует та,
что пришла второй.

## Модель состояний

Состояние живёт на паре **(ревью × ревьювер)**, а не на ревью: один может уже
апрувнуть, пока второй ещё держит мяч.

| Состояние | Смысл | Мяч у | Пингуем |
|---|---|---|---|
| `PENDING` | вердикта нет | ревьювер | да, после SLA |
| `CHANGES_REQUESTED` | ✍️, правки не сделаны | автор | нет |
| `AWAITING_RECHECK` | правки готовы, ✍️ висит | ревьювер | да, после SLA |
| `APPROVED` | 👍 | — | нет |

```
PENDING           --[👍]------------------> APPROVED
PENDING           --[✍️]-----------------> CHANGES_REQUESTED
CHANGES_REQUESTED --[правки закрыты]-----> AWAITING_RECHECK
AWAITING_RECHECK  --[👍]------------------> APPROVED
AWAITING_RECHECK  --[✍️]-----------------> CHANGES_REQUESTED   ← «опять поправить»
APPROVED          --[✍️]-----------------> CHANGES_REQUESTED   ← откат случайного 👍
```

Предпоследний переход — тот самый случай «ревьювер посмотрел правки и попросил ещё»:
мяч уходит автору, пинги гаснут, SLA сбрасывается.

Реализация — [`domain/state.py`](src/reviewpulse/domain/state.py), чистый модуль без I/O.

### Сколько апрувов нужно ревью

`REQUIRED_APPROVALS` (по умолчанию 2) — это **потолок**, а не фиксированное число.
Реальное количество нужных апрувов подстраивается под то, сколько ревьюверов реально
названо в посте:

- назван один ревьювер → достаточно его одного апрува — никто не ждёт второй вердикт,
  который никогда не придёт;
- названы двое → нужны оба;
- названо больше, чем потолок → всё равно нужно ровно `REQUIRED_APPROVALS`, длинный
  список ревьюверов не превращается в требование единогласного апрува.

Реализация — [`services/reviews.py:approvals_needed`](src/reviewpulse/services/reviews.py).

## Рабочее время

И SLA (2 ч), и интервал повторов (20 мин) тикают **только внутри рабочего окна**
09:00–18:00 UTC+3, Пн–Пт по умолчанию. Пост в 17:30 пятницы → дедлайн в 10:30
понедельника. Ночью и в выходные не уходит ничего.

Арифметика — [`domain/workhours.py`](src/reviewpulse/domain/workhours.py).
Производственный календарь пока не учитывается; точка расширения — `is_working_day`.

**Антиспам:** не больше `MAX_NUDGES_PER_DAY` (8) напоминаний в день на пару, кнопки
«🔕 Час» / «🔕 До завтра» в каждой личке, команда `/mute 2h`. Пользователь,
заблокировавший бота, исключается из выборки, а не ретраится каждую минуту.

## Как бот узнаёт, что замечания закрыты

**Режим A (по умолчанию).** Автор жмёт «✅ Поправил» в карточке — все ревьюверы с
✍️ переходят в `AWAITING_RECHECK`.

**Режим B (`GITLAB_ENABLED=true` + токен).** Бот сам опрашивает GitLab и смотрит треды:

- все resolvable-треды ревьювера закрыты во **всех** MR ревью → «правки готовы»;
- появился новый незакрытый тред от него → «опять поправить», пинги гаснут.

Второе правило — независимый от кнопок способ поймать возврат ревьювера: даже если он
оставил замечание только в GitLab и карточку не трогал, бот замолчит.

Ревьювер связывается с GitLab-логином через `/link <логин>`. Без маппинга используется
MR-wide флаг `blocking_discussions_resolved` — грубее, но лучше, чем ничего.
Апрувнутых ревьюверов синк не трогает, чтобы чужой переоткрытый тред не отзывал 👍.

## Статистика по команде

Периодический дайджест в личку — две цифры по каждому человеку: сколько времени
автор тратит на правки после «нужны правки», и сколько времени ревьювер тратит до
первого вердикта — берётся медиана, не среднее, чтобы один нетипичный ответ не
перекашивал число при маленькой выборке. Самые медленные — в начале списка.

Оба числа считаются в рабочем времени, по тому же календарю, что и
[Рабочее время](#рабочее-время) ниже — «нужны правки» в пятницу в 17:30 и ответ в
понедельник в 09:30 — это час, а не ~64 часа с учётом выходных.

Ничего не отправляется, пока не настроен хотя бы один получатель:

```dotenv
STATS_REPORT_RECIPIENT_IDS=123456789,987654321
STATS_REPORT_INTERVAL_DAYS=7
```

Тот же дайджест доступен по запросу через `/stats` — только тем же получателям: это
персональные данные о скорости конкретных людей.

Считает только с момента, когда бот начал вести эту историю переходов — данные по
ревью, закрытым до этого, не восстановить.

## Поддержка языков

Поддерживаются: русский, английский, испанский, итальянский, китайский
(`ru`, `en`, `es`, `it`, `zh`).

Языком управляют две разные вещи, и это не одно и то же:

- **Общая карточка и подсказка «напишите /start»** живут в ветке комментариев — все,
  кто её видит, видят одно и то же сообщение, поэтому язык у них ровно один:
  `DEFAULT_LOCALE` (по умолчанию `en`).
- **Личка** — напоминания, `/start`, `/status`, ответы на кнопки — следует языку
  каждого ревьювера отдельно: то, что он выбрал через `/lang`, иначе язык клиента
  Telegram, иначе `DEFAULT_LOCALE`.

```bash
/lang ru   # переключить свою личку на русский
/lang      # список доступных языков
```

Таблицы переводов — в [`telegram/texts.py`](src/reviewpulse/telegram/texts.py);
разрешение локали — в [`i18n.py`](src/reviewpulse/i18n.py). Тест проверяет, что во
всех пяти языках одинаковый набор ключей — строка, добавленная в один язык и забытая в
другом, ломает CI, а не тихо откатывается на английский в проде.

## Управление через бота

Три вещи редактируются прямо в Telegram, без редеплоя: **у кого есть доступ
администратора**, **пул ревьюверов каждого продукта** и **обязательный ревьюер
каждого продукта** — всё, что использует `/announce`.

- **`/admins`** — видно всем, показывает, у кого сейчас есть доступ администратора
  (тот же принцип «посмотреть можно всем, поменять — не всем», что и у `/products`).
- **`/manage`** — только для админов, открывает панель с пятью действиями:
  добавить/убрать участника пула ревьюверов, сменить обязательного ревьюера продукта,
  добавить/убрать админа. Права перепроверяются на каждое нажатие кнопки, а не только
  при открытии панели — на случай, если кто-то дотянется до неё, повторно отправив
  старый callback или введя текст кнопки вручную. У каждого запроса есть кнопка
  **Отмена** — выйти из процесса посреди диалога больше не значит специально вводить
  что-то невалидное.

Добавление в пул сначала спрашивает, в пул какого продукта — по кнопке на каждый
настроенный продукт, плюс **🌐 все продукты**, чтобы добавить человека сразу везде.
Выбор одного продукта не трогает остальные: тот, кого добавили только в пул
«Платежей», никогда не попадёт в выборку для «Каталога». Глобальный («все продукты»)
участник и участник конкретного продукта могут сосуществовать — это избыточно, но не
конфликт — а удаление одного никогда не затрагивает другого; в списке на удаление
глобальная запись помечена отдельно, чтобы было понятно: удалив её там, человек
пропадёт из пулов всех продуктов, а не только того, который сейчас редактируется.
В любом случае это просто `@username` — как и ручное упоминание ревьювера, имя
разрешается лениво и не требует, чтобы человек хоть раз писал боту `/start`.
Добавление *админа* это требует (права определяются по числовому Telegram id, а не по
имени), так что `/manage` попросит сначала написать `/start`, если бот ещё не видел
этого человека.

Смена обязательного ревьюера работает так же, только без варианта «все продукты» —
обязательный ревьюер всегда относится только к своему продукту, так что это один тап
на продукт, потом `@username` (или **🚫 Без обязательного**, чтобы полностью его
убрать — у продукта вполне может не быть обязательного ревьюера). Переопределение
полностью заменяет собственное значение `techlead` из `REVIEW_PROJECTS` — в том числе
при проверке «выбирают ли эти проекты ревьюверов одинаково», которую `/announce`
выполняет, когда черновик называет MR из нескольких репозиториев: два репозитория,
которые расходятся в `.env`, но имеют одинаковое переопределение через `/manage`, на
практике совпадают — и наоборот.

Список админов изначально заполняется из `ADMIN_USER_IDS` в `.env` — списка числовых
id через запятую, который учитывается только пока таблица админов в БД пуста. В
момент, когда через бота добавлен первый админ, этот список из `.env` перестаёт
учитываться вообще — он существует только как способ стартовать/восстановиться
(первый деплой, или маловероятный случай, когда все админы удалили себя), а не как
постоянный список поверх базы.

## Переназначение ревьювера

Если названный ревьювер ушёл в отпуск или просто оказался не тем человеком, раньше
нужно было вручную редактировать пост в канале и надеяться, что бот правильно его
переразберёт. **`/myposts`** — доступно всем, без прав админа — показывает твои
собственные открытые посты (находятся по строке «Автор:», по тому же полю, в которое
и так уходят DM про просьбу поправить) и позволяет заменить любого названного
ревьювера на другого человека из пула этого продукта прямо в боте.

Нажми на пост, чтобы увидеть его текущих ревьюверов, нажми **🔁** рядом с тем, кто
уходит, затем выбери замену. Старое назначение снимается так же, как при
редактировании поста, когда ревьювер из него пропадает, — его вердикт, если был,
перестаёт учитываться в кворуме, но остаётся в истории — а новое стартует как при
обычном назначении: ожидание вердикта, таймер SLA с этого момента. Карточка в ветке
обсуждения обновляется сразу; текст самого поста в канале не трогается, как и всегда —
переписываются только отслеживаемое состояние и карточка.

Закрытые посты в списке не показываются — закрытому ревью уже нечего переназначать.
Список замены исключает автора поста и всех, кто уже активный ревьювер на нём, так что
задвоить или случайно назначить самого себя не получится.

## Команды бота

| Команда | Что делает |
|---|---|
| `/start` | регистрация; привязывает @ник к id и находит висящие ревью |
| `/status` | что сейчас висит на тебе, с дедлайнами и ссылкой на каждый пост |
| `/announce` | собрать пост для канала за тебя — см. [Автогенерация поста](#автогенерация-поста) |
| `/products` | список продуктов, их обязательный ревьювер и пул каждого |
| `/myposts` | переназначить ревьювера в своих уже опубликованных постах — см. [Переназначение ревьювера](#переназначение-ревьювера) |
| `/admins` | кто сейчас имеет доступ администратора — см. [Управление через бота](#управление-через-бота) |
| `/manage` | добавить/убрать участников пула ревьюверов, сменить обязательного ревьюера продукта, добавить/убрать админов — только для админов |
| `/link <логин>` | связать с аккаунтом GitLab (для режима B) |
| `/lang <код>` | сменить язык бота для своей личной переписки |
| `/mute 2h`, `/unmute` | не беспокоить / снова беспокоить |
| `/stats` | дайджест статистики по запросу — только настроенным получателям, см. [Статистика по команде](#статистика-по-команде) |

## Разработка

```bash
poetry env use 3.12
poetry install
cp .env.example .env                # вписать BOT_TOKEN
poetry run python -m reviewpulse    # миграции применятся сами при старте

poetry run pytest                   # 351 тест
poetry run ruff check src tests
```

Покрыто главное: арифметика рабочего времени (пятница 17:30 → понедельник 10:30),
все рёбра автомата, включая «опять поправить», динамический порог апрувов, парсер на
реальном формате постов и на строгом шаблоне, разбор тредов GitLab на фикстурах,
полнота таблиц перевода по всем пяти языкам и полный цикл через живую SQLite с
сохранностью состояния после рестарта.

Собрать и опубликовать свой образ:

```bash
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ВАШ_АККАУНТ/reviewpulse:latest --push .
```

**Ручной прогон.** Заведите тестовый канал с привязанной группой обсуждений, сделайте
бота админом в обоих, и ускорьте время в `.env`:

```dotenv
SLA_MINUTES=1
RECHECK_SLA_MINUTES=1
NUDGE_INTERVAL_MINUTES=1
WORK_START=00:00
WORK_END=23:59
WORK_DAYS=0,1,2,3,4,5,6
```

Тогда весь цикл — пинг → ✍️ → «Поправил» → пинг recheck → ✍️ снова → тишина →
👍 ×2 → закрытие — проходится за несколько минут.

## Известные ограничения

- **Кто нажал «✅ Поправил», не проверяется.** Пост в канале анонимен — Telegram не
  сообщает автора, поэтому кнопка доступна любому участнику обсуждения.
- **Реакции на самом посте бот не видит** (см. выше). Источник правды — карточка.
- **При закрытии ревью пост в канале удаляется** (набрался кворум апрувов, или нажали
  «🗄 Закрыть») — не сразу, а спустя `CHANNEL_CLEANUP_DELAY_HOURS` (по умолчанию 4
  часа), чтобы пост ещё какое-то время оставался виден. Файлы, приложенные к посту,
  удаляются так же. Тред обсуждения, включая карточку и все комментарии, не
  трогается, чистится только лента канала. Нужно право **Удаление сообщений** у
  бота-админа; без него удаление повторяется на каждом следующем тике. Bot API
  Telegram категорически не позволяет ни одному боту удалить сообщение старше 48
  часов — если ревью закрывается необычно долго, пост может состариться дальше этого
  порога ещё до того, как сработает отложенная очистка, и никакие повторные попытки
  это уже не исправят. Бот распознаёт именно этот случай, прекращает попытки и один
  раз пишет об этом админам в личку, чтобы пост можно было удалить вручную (48-часовое
  ограничение — только для ботов; у обычного аккаунта такого ограничения нет).
- **Производственный календарь не учитывается** — государственный праздник бот будет
  считать обычным рабочим днём.
- **Разбор поста понимает фиксированный набор слов-меток** по каждому полю (см.
  [Как это выглядит](#как-это-выглядит)) — метка вне этого списка, на любом языке,
  обрабатывается позиционной эвристикой, а не читается напрямую.
- **`/announce` требует, чтобы у всех упомянутых проектов совпадал набор
  ревьюверов** — черновик со ссылками на MR из нескольких репозиториев в порядке,
  если их записи в `REVIEW_PROJECTS` совпадают по техлиду/reviewer_count (разный
  `product` сам по себе не проблема); если нет — черновик отклоняется с именами
  конфликтующих проектов, а не молча берётся первый попавшийся.
- **Незаконченный `/announce` не переживает перезапуск** — пошаговый сбор держит
  ответы в памяти, так что редеплой посреди диалога означает начать заново. Готовый
  черновик лежит в БД и не страдает.
- **Статистика считается только с момента, когда фича появилась** — восстановить
  данные по ревью, закрытым раньше, чем появилась эта история переходов, нельзя.
- **`/myposts` находит только посты со строкой «Автор:» на твоё имя** — сопоставление
  по Telegram-юзернейму, так что пост, написанный за тебя без этой строки, не
  попадёт в список; заменить можно только уже названного ревьювера, а не добавить
  ещё одного сверх исходного числа или убрать совсем.
